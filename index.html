日常用户

案例：AI 时代新范式下的 PM

产品经理需要重点维护哪些资产？

PM 的角色从"写 PRD 协调工程"转变为"定义约束、验证产出、控制迭代"。以下按三层管控模型组织。

锚点层 — 极少变动，一改全局对齐 2-3 次/项目

AGENTS.md（项目级 AI 指令文件）

项目级 AI 指令文件。定义技术栈、编码规范、架构边界。AI Agent 直接消费，是所有下游产出的参照系。

Design Brief（设计简报）

一页纸：业务目标+用户+策略+标准+约束。替代几十页 PRD，是所有下游设计/开发产出的起点锚点。

ADR（架构决策记录）

技术选型决策+上下文+约束+后果。PM 做技术决策时留痕，AI 执行时参考，防止"为什么选这个方案"的反复讨论。

Design Tokens（设计规范 JSON）

机器可读设计规范：色彩、字体、间距、圆角、阴影、动效参数。确保多人 AI 产出视觉一致。
进度层 — 随进度增量追加 每迭代追加

BDD Scenarios（行为驱动开发场景）

Given/When/Then 格式的行为规格。可执行的 PRD——AI 从中自动生成测试代码。随功能推进增量追加。

Sitemap（站点地图）

信息架构骨架：主导航+页面层级+路由命名。AI 从 Brief+用户故事自动生成。随功能增加增量追加页面。

Edge Case Matrix（异常态矩阵）

每屏×6 大状态（空/加载/错误/边界数据/权限/离线）穷举。防止 AI 只生成 happy path。PM 主动定义异常态。
执行层 — 发布前验证 每次发布必跑

AC Trace Matrix（验收追溯矩阵）

每功能×AC（验收标准）完成状态矩阵。替代传统 Story Point 估点和燃尽图。PM 用 AC 完成率追踪进度。

Design QA Report（设计走查报告）

实现 vs Design Tokens 偏差清单。AI 自动对比代码与 token 定义，输出 deviations（偏差）列表。PM 判断哪些需要修复。
聚焦指南：每个角色最该维护什么

三个角色，三份清单

32 项资产不需要每个人都管。以下是三个关键角色的"最小维护清单"——只维护这些，就能让 Agent 从"能用"变成"好用"。

作为个人，最应该维护哪些？ 3 项核心资产

个人记忆库（Memory）

你的偏好、习惯、历史决策。Agent 通过记忆库"记住"你，下次交互更顺畅。维护方式：主动告诉 Agent 你的偏好（如"我喜欢用柱状图""代码风格用 Prettier"），Agent 会自动存入记忆。

快捷指令（Prompt Templates）

你高频操作的"一键触发"。维护方式：把重复性操作封装成快捷指令（如"日报生成""代码审查""会议纪要"），下次直接调用，节省 80% 的重复输入时间。

个人知识库（Knowledge Base）

你的私有文档、笔记、参考资料。维护方式：上传个人文档到知识库，Agent 回答时会优先参考你的私有知识，而不是通用知识。
作为团队负责人，最应该维护哪些？ 5 项核心资产

团队知识库（Team Knowledge Base）

产品文档、FAQ、流程规范、最佳实践。维护方式：建立团队文档中心，定期更新，确保所有人用同一个 Agent 时获得一致的回答。

共享技能库（Shared Skills）

团队共用的工作流封装。维护方式：把团队高频操作封装成技能（如"需求评审""设计走查""代码合并"），避免每个人重复造轮子。

工作流编排（Workflow）

跨角色、跨系统的自动化流程。维护方式：定义团队标准流程（如"需求→设计→开发→测试→发布"），让 Agent 自动串联，减少人工协调成本。

权限模型（Permission / RBAC）

谁能看什么、做什么。维护方式：按角色定义权限（如"产品经理可编辑需求，工程师可编辑代码，设计师可编辑设计稿"），确保数据隔离和操作合规。

全局指令（System Prompt）

Agent 的"宪法"。维护方式：和团队对齐 Agent 的行为基线（如"回答必须引用来源""代码必须符合 PEP8""设计必须遵循 Design Tokens"），确保多人使用时表现一致。

机器可读设计规范。确保多人 AI 产出视觉一致，是设计走查的参照基准。

BDD Scenarios（行为驱动开发场景）

Given/When/Then 格式的可执行 PRD。AI 从中自动生成测试代码，是验收标准的源头。

Sitemap（站点地图）

信息架构骨架：主导航+页面层级+路由命名。AI 从 Brief+用户故事自动生成，是页面结构的源头。

Edge Case Matrix（异常态矩阵）

每屏×6 大状态穷举。防止 AI 只生成 happy path，是异常态设计的源头。

AC Trace Matrix（验收追溯矩阵）

每功能×AC 完成状态。替代 Story Point 估点，是进度追踪的唯一指标。

Design QA Report（设计走查报告）

实现 vs Design Tokens 偏差清单。AI 自动对比，PM 判断哪些需要修复，是发布前的最后一道关卡。
实操指南

评测 / 基准线 / 迭代

给 AI 中台负责人的三张实操卡。

如何评测？

1
建评测集：从真实对话提取高频场景。初始 200-500 条。
2
定评分标准：5 分制打分。多人标注 Kappa>=0.8。
3
跑评测+出报告：回答三个问题——好了还是差了？差在哪？要回滚吗？

基准线怎么定？

不能拍脑袋。

1
摸底：当前版本跑评测集，记录实际得分。
2
对齐：和业务方确认容忍度。
3
三级线：红线/黄线/绿线。

如何迭代？

1
小步快跑：每次只改一个变量。
2
灰度发布：5%→20%→50%→100%。红线跌破立即回滚。
3
变更必记录：改了什么、为什么、影响什么。
4
定期复盘：每月评测，每季度对齐基准线。
总结：部署一个 AI Agent 本质上是管理 8 大类 32 项资产。每项资产都有 Owner、Consumer 和 Verifier。个人关注"好不好用"，团队关注"一不一致"，运维关注"稳不稳定"，迭代者关注"变好还是变差"，评测者关注"拿什么证明"。
